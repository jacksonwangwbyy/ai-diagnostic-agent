# 测试报告规范 v1

## 1. 目标

本规范定义自动化测试服务在一次运行结束后输出的测试报告格式。

报告用途：

- 展示本次运行的整体结果
- 展示 flow、cycle、step 的执行情况
- 记录失败、跳过、暂停等关键事件
- 支撑后续接口查询、页面展示、问题排查和统计分析

v1 报告格式支持：

- `json`
- `html`

其中：

- `json` 为标准数据源
- `html` 为可读展示层，可由 `json` 渲染生成

## 2. 设计原则

- 报告必须可追溯到唯一 `run_id`
- 报告必须保留配置快照或配置摘要
- 报告必须覆盖成功、失败、暂停三种终态
- 报告必须记录步骤级执行结果
- 报告必须记录最终采用的失败策略
- 报告必须支持“部分报告”，即运行未完整结束也能输出当前已完成结果

## 3. 输出目录建议

建议每次运行单独一个目录：

```text
<report.output_dir>/
  run_20260331_144500_001/
    report.json
    report.html
```

建议目录命名规则：

```text
<run_id>
```

## 4. 文件清单

### 4.1 report.json

标准报告文件，必须生成。

### 4.2 report.html

展示型报告文件，推荐生成。

## 5. 终态定义

报告的最终状态只允许为：

| 状态 | 说明 |
|---|---|
| `completed` | 全部按计划执行完成 |
| `failed` | 因步骤失败或系统异常终止 |
| `paused` | 因外部暂停请求结束 |

## 6. JSON 报告结构

推荐结构如下：

```json
{
  "run_id": "run_20260331_144500_001",
  "job_name": "热杯扣盖贴标稳定性测试",
  "status": "failed",
  "started_at": "2026-03-31T14:45:00+08:00",
  "ended_at": "2026-03-31T15:12:00+08:00",
  "duration_ms": 1620000,
  "operator": "admin",
  "termination_reason": "step_failed",
  "termination_detail": "lid.dispense timeout",
  "config_snapshot": {},
  "summary": {},
  "failure": {},
  "flows": [],
  "steps": [],
  "artifacts": {}
}
```

## 7. 字段定义

### 7.1 顶层字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `run_id` | string | 是 | 本次运行唯一标识 |
| `job_name` | string | 是 | 任务名称 |
| `status` | string | 是 | 终态：`completed`、`failed`、`paused` |
| `started_at` | string | 是 | 开始时间 |
| `ended_at` | string | 是 | 结束时间 |
| `duration_ms` | number | 是 | 运行总时长 |
| `operator` | string/null | 否 | 操作人 |
| `termination_reason` | string | 是 | 终止原因 |
| `termination_detail` | string/null | 否 | 终止详细说明 |
| `config_snapshot` | object | 是 | 本次运行使用的配置快照或裁剪后的配置副本 |
| `summary` | object | 是 | 执行摘要 |
| `failure` | object/null | 否 | 失败详情，非失败场景可为空 |
| `flows` | array | 是 | flow 级统计 |
| `steps` | array | 是 | step 级明细 |
| `artifacts` | object | 否 | 附件路径 |

### 7.2 termination_reason 建议值

| 值 | 说明 |
|---|---|
| `all_completed` | 所有流程全部完成 |
| `step_failed` | 某步骤失败且策略导致运行结束 |
| `paused_by_request` | 外部暂停请求导致运行结束 |
| `internal_error` | 服务内部异常 |

## 8. summary 结构

建议结构：

```json
{
  "flow_count": 1,
  "planned_cycle_count": 1000,
  "completed_cycle_count": 15,
  "total_step_count": 64,
  "success_step_count": 63,
  "failed_step_count": 1,
  "skipped_step_count": 0,
  "retry_step_count": 1,
  "success_rate": 0.984375
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `flow_count` | number | flow 总数 |
| `planned_cycle_count` | number | 计划总循环次数 |
| `completed_cycle_count` | number | 已完成循环次数 |
| `total_step_count` | number | 实际进入执行的步骤总数 |
| `success_step_count` | number | 成功步骤数 |
| `failed_step_count` | number | 失败步骤数 |
| `skipped_step_count` | number | 跳过步骤数 |
| `retry_step_count` | number | 发生过重试的步骤次数 |
| `success_rate` | number | 成功率，可按实际执行步骤计算 |

说明：

- `success_rate` 建议按 `success_step_count / total_step_count`
- 若 `total_step_count = 0`，建议返回 `0`

## 9. failure 结构

仅在 `status = failed` 时必填。

建议结构：

```json
{
  "flow_id": "hot_flow",
  "flow_name": "热杯流程",
  "cycle_index": 16,
  "step_index": 4,
  "step_name": "扣盖",
  "action": "lid.dispense",
  "params": {
    "cup_type": "hot"
  },
  "attempt_count": 2,
  "error_message": "timeout",
  "failure_action": "stop_run",
  "critical": false
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `flow_id` | string | 所属 flow |
| `flow_name` | string | flow 名称 |
| `cycle_index` | number | 第几轮循环，从 `1` 开始 |
| `step_index` | number | 第几个步骤，从 `1` 开始 |
| `step_name` | string | 步骤名称 |
| `action` | string | 动作名 |
| `params` | object | 动作参数 |
| `attempt_count` | number | 最终执行尝试次数 |
| `error_message` | string | 错误信息 |
| `failure_action` | string | 最终采用的失败策略 |
| `critical` | bool | 是否关键步骤 |

## 10. flows 结构

每个 flow 一条记录，建议结构：

```json
[
  {
    "flow_id": "hot_flow",
    "flow_name": "热杯流程",
    "enabled": true,
    "planned_cycles": 1000,
    "completed_cycles": 15,
    "status": "failed",
    "last_cycle_index": 16
  }
]
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `flow_id` | string | flow 标识 |
| `flow_name` | string | flow 名称 |
| `enabled` | bool | 是否启用 |
| `planned_cycles` | number | 计划循环次数 |
| `completed_cycles` | number | 已完整完成的循环次数 |
| `status` | string | `completed`、`failed`、`paused`、`partial` |
| `last_cycle_index` | number | 最后执行到的循环序号 |

说明：

- 若 flow 未完整结束但运行结束，可用 `partial`

## 11. steps 结构

`steps` 为明细数组，是 v1 报告最核心的数据来源。

建议结构：

```json
[
  {
    "flow_id": "hot_flow",
    "flow_name": "热杯流程",
    "cycle_index": 16,
    "step_index": 4,
    "step_name": "扣盖",
    "action": "lid.dispense",
    "params": {
      "cup_type": "hot"
    },
    "status": "failed",
    "success": false,
    "attempt_count": 2,
    "timeout_ms": 12000,
    "retry_times": 1,
    "critical": false,
    "failure_action": "stop_run",
    "error_message": "timeout",
    "start_time": "2026-03-31T15:11:20+08:00",
    "end_time": "2026-03-31T15:12:00+08:00",
    "duration_ms": 40000
  }
]
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `flow_id` | string | flow 标识 |
| `flow_name` | string | flow 名称 |
| `cycle_index` | number | 第几轮循环 |
| `step_index` | number | 第几个步骤 |
| `step_name` | string | 步骤名称 |
| `action` | string | 动作名 |
| `params` | object | 动作参数 |
| `status` | string | `success`、`failed`、`skipped` |
| `success` | bool | 是否成功 |
| `attempt_count` | number | 执行尝试次数 |
| `timeout_ms` | number | 本步骤超时配置 |
| `retry_times` | number | 本步骤重试配置 |
| `critical` | bool | 是否关键步骤 |
| `failure_action` | string/null | 若失败，则记录最终失败策略 |
| `error_message` | string/null | 错误信息 |
| `start_time` | string | 步骤开始时间 |
| `end_time` | string | 步骤结束时间 |
| `duration_ms` | number | 步骤耗时 |

说明：

- 对成功步骤，`failure_action` 和 `error_message` 可为空
- 对跳过步骤，`status = skipped`，`success = false`

## 12. artifacts 结构

建议结构：

```json
{
  "json_report_path": "/data/test-runner/reports/run_20260331_144500_001/report.json",
  "html_report_path": "/data/test-runner/reports/run_20260331_144500_001/report.html"
}
```

如果未来增加日志归档、原始执行记录，也可继续扩展：

- `runtime_log_path`
- `error_log_path`
- `config_snapshot_path`

## 13. HTML 报告建议内容

HTML 报告可由 `report.json` 渲染生成，建议至少包含以下内容：

### 13.1 基本信息区

- 任务名称
- `run_id`
- 运行状态
- 开始时间
- 结束时间
- 总耗时
- 终止原因

### 13.2 汇总统计区

- flow 总数
- 计划循环次数
- 已完成循环次数
- 成功步骤数
- 失败步骤数
- 跳过步骤数
- 成功率

### 13.3 失败摘要区

仅在失败场景显示：

- 失败 flow
- 失败 cycle
- 失败步骤
- 失败动作
- 错误信息
- 最终失败策略

### 13.4 Flow 执行区

按 flow 展示：

- flow 名称
- 计划循环次数
- 已完成循环次数
- flow 状态

### 13.5 Step 明细区

表格字段建议：

- flow
- cycle
- step index
- step name
- action
- params
- status
- attempt count
- failure action
- duration
- error message

## 14. 暂停场景要求

当运行因暂停结束时：

- `status = paused`
- `termination_reason = paused_by_request`
- 必须输出当前已完成的 flow、cycle、step 数据
- 未执行步骤不进入 `steps` 数组
- 允许 `completed_cycle_count < planned_cycle_count`

## 15. 跳过场景要求

当因失败策略触发 `skip_step` 或 `skip_flow` 时：

- 对失败步骤：
  - `status = failed`
  - `failure_action = skip_step` 或 `skip_flow`
- 若某一步骤因策略未执行：
  - 可不生成记录
  - 或生成 `status = skipped` 记录

v1 建议：

- 对“执行过但失败”的步骤记录为 `failed`
- 对“明确被调度器跳过”的步骤记录为 `skipped`

这样报告信息更完整。

## 16. 配置快照要求

`config_snapshot` 建议保留本次实际使用的配置内容，以避免后续原配置被修改后无法追溯。

可选方案：

- 直接嵌入完整配置对象
- 嵌入裁剪后的关键字段
- 另存为文件并在报告中引用路径

v1 推荐：

- `report.json` 内直接嵌入配置对象

## 18. 实现建议

- 所有步骤执行完成后立即落一条 step record，避免异常时丢数据
- 运行结束时再汇总生成 summary、failure、flows
- `report.html` 尽量由 `report.json` 单向生成，避免双份逻辑
- 生成报告时建议原子写入，避免半成品文件被查询到

## 19. v1 范围说明

本版本暂不包含以下能力：

- 图表型趋势分析
- MTBF 统计
- AI 分析摘要
- 多运行对比报告
- PDF / DOC 报告输出

以上能力可在 v2 继续扩展。
