**流程图说明:**

1. **客户端 (Client)**:  
   * 发起 acquire\_lock 请求。  
   * 根据返回的 LockResult：  
     * 如果成功并获得 ACQUIRED 状态和 Token，则使用 Token 执行需要锁保护的操作，完成后调用 release\_lock。  
     * 如果返回 PENDING 状态，则调用 wait\_for\_lock 等待锁请求的最终结果（可能是成功获取、超时或被取消）。  
     * 如果立即失败，则处理失败逻辑。  
2. **锁管理器 \- acquire\_lock 核心逻辑**:  
   * 接收请求后，进行前置检查与幂等性判断（输入参数的有效性、队列容量是否已满、以及 request\_id\_hint 是否已存在且有效，用于处理重复请求）。  
   * 尝试立即授予锁：检查所需硬件是否都可用（硬件物理上可用），并且根据公平性策略——如等待队列中没有优先级更高且请求相同资源的请求——判断是否可以立即授予（避免低优先级请求饿死高优先级请求）。  
   * 如果可以立即授予，则更新内部状态，生成 Token，并返回成功的 LockResult。  
   * 如果不能立即授予：  
     * 若请求配置为不等待 (wait\_timeout\_ms \== 0)，则标记请求为已取消或超时，并返回失败。  
     * 否则，将请求加入等待队列，并返回 PENDING 状态的 LockResult。  
3. 锁管理器 \- 后台任务 (并发执行):  
   后台任务在一个周期性循环中运行，每个循环内会依次执行以下两个主要阶段：首先，全面检查并处理所有当前已授予锁的过期情况；然后，处理等待队列中的所有请求。  
   * **检查已持有锁是否过期**: 定期检查当前所有已被授予的锁。如果发现某个锁的持有时间超过了其 default\_lock\_hold\_timeout\_ms，则会自动释放该锁，并将持有该锁的原始请求的状态更新为 LOCK\_EXPIRED。这会触发相应请求的事件。  
   * **处理等待队列**:  
     * 按优先级遍历等待队列中的请求。  
     * 对每个等待中的请求，检查其自身的等待超时 (request.wait\_timeout\_ms) 是否已到。如果已到，则将该请求标记为 TIMED\_OUT，从等待者中移除，并触发其事件。  
     * 如果请求未超时，则检查其所需的硬件资源当前是否可用（硬件物理上可用）且符合公平性策略（例如，等待队列中没有优先级更高且请求相同资源的请求）。如果满足条件，则将锁授予该请求（逻辑类似 acquire\_lock 中的立即授予部分），并触发其事件。  
4. **锁管理器 \- release\_lock 核心逻辑**:  
   * 接收到 release\_lock 请求后，验证提供的 Token 是否有效以及是否确实持有所声明要释放的硬件锁。  
   * 如果有效，则释放指定的硬件锁：更新硬件的 LockInfo 状态，从活动 Token 列表中移除相应记录。如果原始锁请求的状态是 ACQUIRED，可能会将其更新为 LOCK\_RELEASED。  
   * 锁释放后，会尝试处理等待队列，看是否有其他等待的请求现在可以获得锁。  
   * 返回操作结果（对应RL5）。如果提供的Token无效，或者Token有效但并不实际持有请求释放的硬件锁，则释放操作失败，系统不会更改任何锁的状态，并向客户端返回相应的错误信息和指示操作未成功的状态（对应RL6）。

**关键交互点**:

* wait\_for\_lock 的客户端调用会阻塞，直到其对应的 LockRequest 的内部事件 (threading.Event) 被设置。  
* 这个事件可以由多种情况触发：  
  * acquire\_lock 内部直接授予锁。  
  * 后台任务处理等待队列时授予锁。  
  * 后台任务处理等待队列时发现请求等待超时。  
  * 后台任务处理已持有锁时发现锁过期。  
  * release\_lock 或 force\_release\_all\_locks 间接触发状态改变。

这个流程图旨在提供一个清晰的概览，帮助理解锁的完整生命周期和管理器各部分之间的协作。
