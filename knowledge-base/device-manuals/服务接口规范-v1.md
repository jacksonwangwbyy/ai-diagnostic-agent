# 自动化测试服务接口规范 v1

## 1. 目标

本规范定义自动化测试服务对外提供的控制和查询接口。

服务目标：

- 接收测试配置文件
- 启动一次测试运行
- 支持暂停当前运行
- 查询当前运行状态和进度
- 查询测试报告列表和详情

本规范默认服务通过 HTTP API 暴露能力，后续可在此基础上扩展页面或 CLI。

## 2. 设计约束

- 同一时刻只允许一个运行中的测试任务
- `start` 调用成功后生成唯一 `run_id`
- `pause` 只影响当前运行中的 `run_id`
- 暂停后本次运行结束，并生成部分报告
- 再次开始时从头执行，不做断点续跑
- 配置文件校验失败时，不进入执行态
- 所有接口返回统一响应结构

## 3. 基础约定

### 3.1 Base URL

示例：

```text
http://<host>:<port>/api/v1
```

### 3.2 统一响应结构

```json
{
  "success": true,
  "code": "OK",
  "message": "success",
  "data": {}
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `success` | bool | 请求是否成功 |
| `code` | string | 结果码 |
| `message` | string | 结果说明 |
| `data` | object/null | 业务数据 |

### 3.3 时间格式

统一使用 ISO 8601 字符串，例如：

```text
2026-03-31T14:45:00+08:00
```

## 4. 状态定义

### 4.1 运行状态

| 状态 | 说明 |
|---|---|
| `idle` | 当前没有运行中的任务 |
| `validating` | 正在校验配置 |
| `running` | 正在执行 |
| `pausing` | 已接收暂停请求，正在结束当前运行 |
| `paused` | 本次运行因暂停结束 |
| `completed` | 全部执行完成 |
| `failed` | 因步骤失败或系统异常结束 |

说明：

- `paused`、`completed`、`failed` 都是终态
- 服务层面始终只保留一个“当前运行态”，但可查询历史报告

### 4.2 步骤结果状态

| 状态 | 说明 |
|---|---|
| `pending` | 未执行 |
| `running` | 执行中 |
| `success` | 执行成功 |
| `failed` | 执行失败 |
| `skipped` | 按失败策略被跳过 |

## 5. 错误码建议

| 错误码 | 说明 |
|---|---|
| `OK` | 成功 |
| `INVALID_REQUEST` | 请求参数非法 |
| `CONFIG_INVALID` | 配置文件不合法 |
| `RUN_ALREADY_ACTIVE` | 已存在运行中的任务 |
| `NO_ACTIVE_RUN` | 当前没有运行中的任务 |
| `RUN_NOT_FOUND` | 指定运行不存在 |
| `REPORT_NOT_FOUND` | 指定报告不存在 |
| `INTERNAL_ERROR` | 服务内部错误 |

## 6. 接口清单

v1 建议提供以下接口：

- `POST /runs/start`
- `POST /runs/pause`
- `GET /runs/current`
- `GET /runs/{run_id}`
- `GET /runs/{run_id}/progress`
- `GET /reports`
- `GET /reports/{run_id}`

## 7. 接口定义

### 7.1 开始测试

`POST /runs/start`

说明：

- 接收测试配置文件内容或配置文件路径
- 成功后创建新的 `run_id`
- 若已有运行中的任务，则拒绝启动

请求体建议：

```json
{
  "config_source_type": "inline",
  "config_content": "version: 1\njob:\n  name: demo\n..."
}
```

或：

```json
{
  "config_source_type": "file_path",
  "config_file_path": "/data/test-runner/configs/demo.yaml"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `config_source_type` | string | 是 | `inline` 或 `file_path` |
| `config_content` | string | 否 | `inline` 模式下的 YAML 内容 |
| `config_file_path` | string | 否 | `file_path` 模式下的配置文件路径 |
| `operator` | string | 否 | 操作人 |

响应示例：

```json
{
  "success": true,
  "code": "OK",
  "message": "run started",
  "data": {
    "run_id": "run_20260331_144500_001",
    "status": "running",
    "started_at": "2026-03-31T14:45:00+08:00"
  }
}
```

失败示例：

```json
{
  "success": false,
  "code": "RUN_ALREADY_ACTIVE",
  "message": "another run is active",
  "data": {
    "run_id": "run_20260331_143000_001",
    "status": "running"
  }
}
```

### 7.2 暂停测试

`POST /runs/pause`

说明：

- 请求暂停当前运行
- 服务收到请求后，将当前运行状态切换为 `pausing`
- 当前运行结束后，状态进入 `paused`

请求体建议：

```json
{
  "reason": "manual pause",
  "operator": "admin"
}
```

响应示例：

```json
{
  "success": true,
  "code": "OK",
  "message": "pause requested",
  "data": {
    "run_id": "run_20260331_144500_001",
    "status": "pausing",
    "requested_at": "2026-03-31T14:55:00+08:00"
  }
}
```

### 7.3 查询当前运行

`GET /runs/current`

说明：

- 返回当前活跃运行
- 若当前没有活跃运行，返回最近一次运行或返回空，二选一即可

推荐返回当前状态快照。

响应示例：

```json
{
  "success": true,
  "code": "OK",
  "message": "success",
  "data": {
    "run_id": "run_20260331_144500_001",
    "status": "running",
    "job_name": "热杯扣盖贴标稳定性测试",
    "started_at": "2026-03-31T14:45:00+08:00",
    "current_flow_id": "hot_flow",
    "current_flow_name": "热杯流程",
    "current_cycle": 16,
    "total_cycles": 1000,
    "current_step_index": 3,
    "current_step_name": "扣盖前检查",
    "current_action": "lid.pre_check"
  }
}
```

### 7.4 查询指定运行

`GET /runs/{run_id}`

说明：

- 返回指定运行的完整摘要

响应示例：

```json

  "message": "success",
  "data": {
```

说明：

- 返回历史运行报告列表

| `page` | number | 否 | 页码 |
| `page_size` | number | 否 | 每页数量 |

## 8. 运行规则

### 8.1 单运行约束

- 服务同一时刻只允许一个 `running` 或 `pausing` 状态的任务
- 若已有活跃任务，新的 `start` 请求直接返回 `RUN_ALREADY_ACTIVE`

### 8.2 开始流程

建议内部执行顺序：

1. 接收配置
2. 校验配置结构和动作合法性
3. 生成 `run_id`
4. 写入运行记录
5. 切换状态为 `running`
6. 异步开始执行

### 8.3 暂停流程

建议内部执行顺序：

1. 接收暂停请求
2. 将运行标记为 `pausing`
3. 调度器不再发起后续新步骤
4. 当前运行结束后切换为 `paused`
5. 生成部分报告

### 8.4 失败策略联动

服务实现必须和配置文件规范中的失败策略保持一致。

当步骤执行失败且重试耗尽后：

- 若最终失败策略为 `stop_run`，则运行状态进入 `failed`
- 若最终失败策略为 `skip_step`，则运行状态保持 `running`
- 若最终失败策略为 `skip_flow`，则运行状态保持 `running`，但当前 flow 本轮提前结束

报告中必须保留：

- 实际失败步骤
- 最终采用的失败策略
- 是否触发 `critical`
- 错误信息

## 9. 推荐数据模型

### 9.1 Run

建议字段：

- `run_id`
- `job_name`
- `status`
- `config_snapshot`
- `started_at`
- `ended_at`
- `termination_reason`
- `termination_detail`
- `operator`

### 9.2 StepRecord

建议字段：

- `run_id`
- `flow_id`
- `flow_name`
- `cycle_index`
- `step_index`
- `step_name`
- `action`
- `params`
- `attempt_count`
- `status`
- `success`
- `failure_action`
- `error_message`
- `start_time`
- `end_time`
- `duration_ms`

## 10. 实现建议

- `start` 接口建议只负责接收和校验，不阻塞等待整个测试完成
- 执行器建议后台线程或独立 worker 驱动
- `pause` 建议做成“协作式暂停”，即在步骤边界或动作返回后生效
- `GET /runs/current` 应尽量轻量，适合前端轮询
- `GET /reports/{run_id}` 可直接读取落盘后的 JSON 报告并返回

## 11. v1 范围说明

本版本暂不包含以下能力：

- 终止并强制中断底层硬件动作
- 多任务并发运行
- 用户权限和鉴权
- WebSocket 实时推送
- 报告删除接口
- 配置模板管理接口

后续如需要，可在 v2 扩展。
