# 执行状态机设计

## 1. 目标

本设计用于定义自动化测试服务在一次运行生命周期中的状态、事件、状态迁移和执行规则。

目的：

- 明确 `start / pause / failure / complete` 的行为边界
- 明确调度器如何推进 flow、cycle、step
- 明确失败策略与状态机的联动
- 为后续代码实现提供稳定模型

## 2. 设计原则

- 同一时刻只允许一个活跃运行
- 服务状态与运行状态保持一致
- 暂停采用协作式暂停，不直接中断底层设备动作
- 状态切换必须可追溯、可落日志、可生成报告
- 报告生成属于运行终态收尾逻辑的一部分

## 3. 状态定义

## 3.1 服务级状态

服务级状态反映“当前是否有活跃运行”。

| 状态 | 说明 |
|---|---|
| `idle` | 当前无活跃运行 |
| `validating` | 正在校验配置 |
| `running` | 正在执行测试流程 |
| `pausing` | 已接收暂停请求，等待当前执行边界结束 |
| `paused` | 本次运行因暂停结束，已生成部分报告 |
| `completed` | 本次运行全部完成，已生成最终报告 |
| `failed` | 本次运行失败结束，已生成失败报告 |

说明：

- `paused`、`completed`、`failed` 都是终态
- 服务可在终态后回到 `idle`

## 3.2 步骤级状态

| 状态 | 说明 |
|---|---|
| `pending` | 未开始 |
| `running` | 执行中 |
| `success` | 成功 |
| `failed` | 失败 |
| `skipped` | 被跳过 |

## 4. 核心对象

## 4.1 RunContext

建议运行期维护一个 `RunContext`，保存本次执行上下文。

建议字段：

- `run_id`
- `job_name`
- `status`
- `config`
- `started_at`
- `ended_at`
- `pause_requested`
- `termination_reason`
- `termination_detail`
- `current_flow_index`
- `current_cycle_index`
- `current_step_index`
- `current_attempt`
- `step_records`
- `flow_records`

## 4.2 Scheduler Cursor

建议单独维护调度游标：

- `flow_index`
- `cycle_index`
- `step_index`

说明：

- 三者共同定位当前运行位置
- 都建议从 `0` 存储，输出报告时转换为从 `1` 开始

## 5. 事件定义

状态机的典型事件如下：

| 事件 | 说明 |
|---|---|
| `START_REQUESTED` | 接收到开始请求 |
| `CONFIG_VALID` | 配置校验通过 |
| `CONFIG_INVALID` | 配置校验失败 |
| `STEP_STARTED` | 当前步骤开始执行 |
| `STEP_SUCCEEDED` | 当前步骤执行成功 |
| `STEP_FAILED` | 当前步骤执行失败 |
| `STEP_RETRY` | 当前步骤进入重试 |
| `PAUSE_REQUESTED` | 接收到暂停请求 |
| `FLOW_COMPLETED` | 当前 flow 当前轮次执行完 |
| `RUN_COMPLETED` | 全部 flow 全部执行完 |
| `RUN_ABORTED` | 因失败策略或内部错误终止 |
| `REPORT_GENERATED` | 报告已生成 |
| `RESET_TO_IDLE` | 运行终态已收尾，服务回到空闲 |

## 6. 状态迁移

## 6.1 服务级迁移图

```text
idle
  -> validating
  -> running

validating
  -> running
  -> idle

running
  -> pausing
  -> completed
  -> failed

pausing
  -> paused
  -> failed

paused
  -> idle

completed
  -> idle

failed
  -> idle
```

## 6.2 状态迁移表

| 当前状态 | 事件 | 下一个状态 | 说明 |
|---|---|---|---|
| `idle` | `START_REQUESTED` | `validating` | 开始接收并校验配置 |
| `validating` | `CONFIG_VALID` | `running` | 创建运行上下文并开始调度 |
| `validating` | `CONFIG_INVALID` | `idle` | 返回配置错误，不创建运行 |
| `running` | `PAUSE_REQUESTED` | `pausing` | 设置暂停标记 |
| `running` | `RUN_COMPLETED` | `completed` | 全部执行完成 |
| `running` | `RUN_ABORTED` | `failed` | 失败终止 |
| `pausing` | `REPORT_GENERATED` | `paused` | 已生成部分报告 |
| `pausing` | `RUN_ABORTED` | `failed` | 暂停阶段若内部异常，转失败 |
| `paused` | `RESET_TO_IDLE` | `idle` | 收尾完成 |
| `completed` | `RESET_TO_IDLE` | `idle` | 收尾完成 |
| `failed` | `RESET_TO_IDLE` | `idle` | 收尾完成 |

## 7. 调度模型

## 7.1 执行顺序

严格顺序执行：

1. 遍历 `flows`
2. 对每个已启用 flow，循环执行 `cycles` 次
3. 每轮 cycle 中按 `steps` 顺序执行

伪代码：

```text
for each flow in flows:
  if not flow.enabled:
    continue

  for cycle in 1..flow.cycles:
    for step in flow.steps:
      execute(step)
```

## 7.2 调度边界

建议只在以下边界检查暂停和状态切换：

- 一个步骤开始前
- 一个步骤完成后
- 一个步骤重试结束后
- 一个 flow 一轮执行结束后

说明：

- 不建议在步骤执行中途强行切断线程
- 调度器只负责“不再发起后续步骤”

## 8. 单步执行状态机

## 8.1 单步执行流程

```text
pending
  -> running
  -> success
  -> failed
  -> skipped
```

## 8.2 单步执行规则

对于一个步骤，建议执行顺序如下：

1. 创建 step record，状态置为 `running`
2. 调用动作执行器
3. 若成功：
   - 记录 `success`
   - 返回调度器进入下一步
4. 若失败：
   - 判断是否仍有剩余重试次数
   - 若有，则进入重试
   - 若无，则计算最终失败策略
5. 根据失败策略：
   - `stop_run`
   - `skip_step`
   - `skip_flow`

## 8.3 重试规则

建议：

- `attempt_count` 从 `1` 开始
- `retry_times = 0` 表示只执行一次，不重试
- 实际最大尝试次数 = `1 + retry_times`

示例：

- `retry_times = 0` -> 最多 1 次
- `retry_times = 1` -> 最多 2 次

## 9. 失败策略联动

## 9.1 策略优先级

失败策略优先级：

1. `step.critical = true` -> 强制 `stop_run`
2. `step.on_failure`
3. `flow.on_failure`
4. `runtime.failure_policy.action`

## 9.2 stop_run

行为：

- 当前步骤标记为 `failed`
- 运行状态转为 `failed`
- 不再执行后续步骤、后续 cycle、后续 flow
- 进入报告生成流程

## 9.3 skip_step

行为：

- 当前步骤标记为 `failed`
- 记录 `failure_action = skip_step`
- 继续执行当前 flow 的下一个步骤

说明：

- 若该步骤本身是关键步骤，不允许 `skip_step`

## 9.4 skip_flow

行为：

- 当前步骤标记为 `failed`
- 记录 `failure_action = skip_flow`
- 当前 flow 当前 cycle 剩余步骤不再执行
- 进入下一个 flow

说明：

- v1 建议：`skip_flow` 直接结束当前 flow 的本轮 cycle，并继续下一个 flow
- 不建议在同一 flow 的下一轮 cycle 中继续执行，避免语义歧义

## 10. 暂停处理

## 10.1 暂停请求

当收到 `pause` 请求时：

1. 校验当前状态是否为 `running`
2. 将 `pause_requested = true`
3. 服务状态从 `running` 切换为 `pausing`

## 10.2 暂停生效时机

建议在以下时机生效：

- 当前步骤结束后
- 当前步骤重试结束后

暂停生效后：

- 不再调度任何新步骤
- 设置 `termination_reason = paused_by_request`
- 进入报告生成流程

## 10.3 暂停与失败冲突

若在 `pausing` 状态下当前步骤最终失败：

- 若实现已决定本次运行结束，则可统一收敛到 `paused`
- 但为了语义准确，建议如下：
  - 如果本次结束的直接原因是失败，状态记为 `failed`
  - 如果本次结束的直接原因是暂停，状态记为 `paused`

推荐规则：

- 当前步骤已开始，且最终失败并触发 `stop_run` 时，优先记为 `failed`

## 11. 报告生成时机

报告生成触发条件：

- 全部完成
- 暂停结束
- 失败终止
- 内部异常终止

建议顺序：

1. 冻结运行上下文
2. 汇总 summary / failure / flows / steps
3. 写出 `report.json`
4. 基于 JSON 生成 `report.html`
5. 状态进入终态

## 12. 幂等性建议

## 12.1 start

- 当已有活跃运行时，新的 `start` 请求必须拒绝
- 不允许重复创建两个 `run_id`

## 12.2 pause

- 当状态已为 `pausing` 时，再次 `pause` 应返回成功或幂等响应
- 当状态不为 `running` 时，应返回 `NO_ACTIVE_RUN`

## 12.3 report generation

- 对同一个 `run_id`，报告生成逻辑应尽量只执行一次
- 若重复触发，应覆盖写入或做幂等保护

## 13. 推荐实现分层

建议拆分为以下模块：

### 13.1 RunManager

职责：

- 管理当前运行上下文
- 管理状态切换
- 暴露 `start / pause / current`

### 13.2 ConfigValidator

职责：

- 校验配置结构
- 校验动作和参数
- 校验失败策略

### 13.3 Scheduler

职责：

- 遍历 flow / cycle / step
- 推进游标
- 处理暂停与失败策略

### 13.4 ActionExecutor

职责：

- 将配置动作映射为 `bar_middleware` 调用
- 返回统一执行结果

### 13.5 ReportBuilder

职责：

- 根据运行上下文构建 JSON 报告
- 渲染 HTML 报告

## 14. 推荐伪代码

```text
start(config):
  assert service_state == idle
  service_state = validating

  validate(config)

  run = create_run_context(config)
  service_state = running

  for flow in config.flows:
    if not flow.enabled:
      continue

    for cycle in range(flow.cycles):
      for step in flow.steps:
        if run.pause_requested:
          finalize_as_paused(run)
          return

        result = execute_step(run, flow, cycle, step)

        if result == success:
          continue

        policy = resolve_failure_policy(step, flow, runtime)

        if policy == stop_run:
          finalize_as_failed(run)
          return

        if policy == skip_step:
          continue

        if policy == skip_flow:
          break

  finalize_as_completed(run)
```

## 15. 关键约束

- 任一时刻只能有一个活跃 `RunContext`
- 状态切换必须串行化处理
- `pause_requested` 必须是线程安全可见的
- step record 建议在每个步骤结束后立即持久化或缓存

## 16. 日志建议

建议每次状态切换都记录日志：

- `from_status`
- `to_status`
- `event`
- `run_id`
- `flow_id`
- `cycle_index`
- `step_index`
- `message`

典型日志点：

- 开始请求
- 配置校验成功/失败
- 步骤开始
- 步骤成功
- 步骤失败
- 步骤重试
- 失败策略决策
- 暂停请求
- 报告生成完成

## 17. v1 范围说明

本设计暂不处理以下场景：

- 多任务并发状态机
- 底层设备动作强制中断状态机
- 分布式调度
- 跨进程恢复运行

如后续需要，可在 v2 扩展。
