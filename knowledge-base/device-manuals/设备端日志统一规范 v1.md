# 无人值守饮品设备 — 设备端日志统一规范 v1

## 一、适用范围

所有相关项目统一输出 JSON 格式日志，每行一条，通过 Fluentd 收集后写入统一文件 `/home/smyze/logs/device_op/devices_op.log`。

| 项目 | 语言 | 当前日志框架 |
| :--- | :--- | :--- |
| `bar_middleware` | Python | loguru (CustomLog) |
| `bar-deploy-client` | Java | SLF4J + Logback |
| `orderStatusAgent` | Python | loguru (CustomLog) |
| `Quokka251` | C# | Microsoft.Extensions.Logging |
| `tools` | Bash | rsyslog / shell |

## 二、字段字典

| 字段 | 类型 | 说明 | 示例 |

## 四、时间格式

统一使用 ISO 8601 带时区偏移，精确到毫秒：

```
YYYY-MM-DDTHH:mm:ss.SSS+08:00
```

**示例**: `2026-03-05T14:35:12.123+08:00`

各项目实现要点：

- **Python**: `datetime.now(timezone(timedelta(hours=8))).strftime('%Y-%m-%dT%H:%M:%S.') + f'{ms:03d}+08:00'`
- **Java**: `DateTimeFormatter.ofPattern("yyyy-MM-dd'T'HH:mm:ss.SSSXXX")`
- **C#**: `DateTime.Now.ToString("yyyy-MM-ddTHH:mm:ss.fffzzz")`
- **Bash**: `date +%Y-%m-%dT%H:%M:%S.%3N+08:00`

## 五、TraceID 规则

### 5.1 格式

```
{前缀}-{设备SN}-{毫秒时间戳}
```

### 5.2 前缀枚举

| 前缀 | 场景 | 生成时机 |
| :--- | :--- | :--- |
| `ORD` | 订单驱动 | 收到下单指令时 |
| `DEV` | 无订单（待机/自检/异常） | 进入待机或触发自检时 |
| `MNT` | 设备维护 | 运维操作触发时 |
| `SYS` | 系统自检 | 定时心跳/系统巡检时 |
| `MATL` | 物料状态变更 | 物料检测触发时 |

### 5.3 示例

```
ORD-C028-1741397130123    # 订单场景
DEV-C028-1741397130456    # 待机自检
MNT-C028-1741397130789    # 维护操作
```

### 5.4 传递规则

- TraceID 在一个完整业务周期内保持不变。
- 订单场景由 `Quokka251` 的 `PrepareTask2` 生成 `ORD-{设备SN}-{时间戳}`，通过以下方式传递：
  - → `bar_middleware`：HTTP Header `X-Trace-ID` / `X-Order-ID`（bar_middleware 中间件自动读取）
  - → `orderStatusAgent`：RabbitMQ 消息体 `trace_id` / `order_id` 字段（消费者自动提取）
- 运维场景由 `bar-deploy-client` 本地生成 `MNT-{设备SN}-{时间戳}`。
- 系统场景由 `tools` 本地生成 `SYS-{设备SN}-{时间戳}` 或 `DEV-{设备SN}-{时间戳}`。

### 5.5 跨项目链路追踪实现

```
Quokka251 PrepareTask2
  │ 生成 trace_id = "ORD-C028-xxx"
  │ Logger.SetTraceContext(traceId, orderId)
  │
  ├──HTTP──→ bar_middleware
  │          Header: X-Trace-ID / X-Order-ID
  │          中间件自动读取并设置到 contextvars
  │
  └──MQ────→ orderStatusAgent
             消息体: {"trace_id":"ORD-C028-xxx","order_id":"ORD-001",...}
             消费者自动提取并设置到 contextvars
```

**查询示例：**
```bash
# 一条命令查看完整订单链路
grep "ORD-C028-1741397110100" /home/smyze/logs/device_op/devices_op.log | jq .
```

```json
{"timestamp":"2026-03-05T14:35:12.123+08:00","level":"ERROR","module":"RoboticArm","module_id":"RA_01","device_id":"C028","trace_id":"ORD-C028-1741397130123","order_id":"ORD-202603051430002","event_type":"operation","source":"bar_middleware","message":"取杯失败：位置超时","details":{"action":"pick_cup","status":"fail","duration_ms":3500,"position":{"x":125.4,"y":330.2,"z":85.0},"retry_count":2,"error_code":"RA-005-0001","original_error_code":""}}
```

---

> #### 关键决策点
> 
> 这是基于五个项目实际代码梳理出来的统一规范 v1。几个关键决策点：
> 
> - **`order_id`**: 非订单场景用空字符串而非 `N/A`，避免索引污染。
> - **`device_id`**: 直接用设备 SN（如 `C028`），不加 `DEV_` 前缀，因为代码里普遍直接使用 SN。
> - **`source`**: 新增此字段用于标识来源项目，方便排查是哪个进程产生的日志。
> - **`deploy`**: 新增此事件类型，以涵盖 `tools` 项目的部署操作日志。
> - **`details.original_error_code`**: Eversys 原始错误码在此字段中保留，以便在过渡期可以双码并存进行对照。

## 十、第一期改造范围与实施方案

### 10.1 改造目标

第一期只改造**关键业务路径和异常路径**的日志，不做全量覆盖。改造后这些日志以 JSON 格式输出到 **stdout**，由 Fluentd 收集后写入统一日志文件 `/home/smyze/logs/device_op/devices_op.log`，各项目原有日志输出保持不变。

### 10.2 日志收集方案

所有项目部署在 Docker 容器中，已配置 Fluentd 作为日志收集器。采用 **stdout + Fluentd** 方案实现日志统一。

**方案：各容器输出 JSON 到 stdout，Fluentd 收集并路由**

```
架构流程：
各容器 → stdout (JSON + log_type 标识) → Fluentd → 统一文件
```

**优势：**
- ✅ 无需修改容器启动脚本（已配置 `--log-driver=fluentd`）
- ✅ 无锁竞争，性能最优
- ✅ 符合 Docker 最佳实践（12-factor app）
- ✅ 配置简单，各语言只需输出 JSON 到 stdout
- ✅ 扩展性强，未来可轻松对接其他日志系统

各语言实现要点：

| 语言 | 实现方式 |
| :--- | :--- |
| Python (`bar_middleware` / `orderStatusAgent`) | loguru 输出到 `sys.stdout`，`serialize=True`，添加 `log_type="device_op"` 字段 |
| Java (`bar-deploy-client`) | Logback Console Appender + LogstashEncoder，添加 `log_type="device_op"` 自定义字段 |
| C# (`Quokka251`) | Serilog Console Sink + CompactJsonFormatter，添加 `log_type="device_op"` 属性 |
| Bash (`tools`) | `echo '{"log_type":"device_op",...}'` 输出 JSON 到 stdout |

**关键约束：**
- 每条日志必须包含 `"log_type": "device_op"` 字段，用于 Fluentd 过滤
- 单行 JSON 控制在合理大小（建议 < 10KB）
- 输出到 stdout，不写文件

### 10.3 日志流转架构

```
原有日志（保留不变）          统一日志收集（新增）
┌─────────────────┐         ┌──────────────────────────────────┐
│ bar_middleware   │         │                                  │
│ logs/*.log       │         │  各容器 stdout (JSON)             │
│ (loguru 各模块)   │         │  ↓                               │
├─────────────────┤         │  Fluentd 收集                     │
│ Quokka251       │         │  ↓                               │
│ Docker logs      │────────▶│  过滤 log_type="device_op"       │
├─────────────────┤         │  ↓                               │
│ bar-deploy-client│         │  /home/smyze/logs/device_op/     │
│ logback files    │────────▶│  devices_op.log                  │
├─────────────────┤         │                                  │
│ order_agent      │         │  所有项目的关键日志                │
│ Docker logs      │────────▶│  统一 JSON 格式                   │
├─────────────────┤         │  一行一条                          │
│ tools            │         │  Fluentd 自动轮转                 │
│ shell logs       │────────▶│                                  │
└─────────────────┘         └──────────────────────────────────┘
```

**原则：只增不改** — 各项目原有日志系统完全保留，统一日志是额外的一路输出到 stdout。

### 10.3.1 多程序写入规则

#### 写入流程

```
各容器进程 → stdout (JSON) → Docker log-driver=fluentd → Fluentd → 统一文件
tools 宿主机脚本 → flock 加锁 → 直接追加写入同一个统一文件
```

容器日志通过 Fluentd 收集写入，tools 宿主机脚本直接写入同一个文件（`/home/smyze/logs/device_op/devices_op.log`），使用 `flock` 文件锁避免并发写入行交错。

#### 各程序输出方式

| 容器 | 输出到 | JSON 标识 |
|------|--------|-----------|
| barMiddleware | stdout | `"log_type":"device_op","source":"bar_middleware"` |
| smyzeModeOperating | stdout | `"log_type":"device_op","source":"quokka"` |
| smyzeHardwareEversys | stdout | `"log_type":"device_op","source":"quokka"` |
| bar-deploy-client | stdout | `"log_type":"device_op","source":"deploy_client"` |
| order_agent / order_agent_websocket | stdout | `"log_type":"device_op","source":"order_agent"` |
| tools（宿主机脚本） | 直写文件（flock 加锁） | `"log_type":"device_op","source":"tools"` |

容器启动时已配置 `--log-driver=fluentd`，Docker 自动将 stdout 转发到 Fluentd（端口 24224）。tools 作为宿主机脚本不经过 Docker/Fluentd，直接通过 `flock` 文件锁追加写入同一个 `devices_op.log` 文件。

#### Fluentd 双路处理

**路径 1（原有，保留不变）：**
```
所有容器日志 → /home/smyze/logs/{容器tag}/docker.log
```
每个容器各自一个文件，与改造前完全一致。

**路径 2（新增）：**
```
所有容器日志 → grep 过滤 "log_type":"device_op" → /home/smyze/logs/device_op/devices_op.log
```
只有包含 `"log_type":"device_op"` 的日志才会进入统一文件，其他日志（普通业务日志、框架日志等）被过滤掉。

#### 日志文件分割

**分割策略：**
- Fluentd buffer 达到 100M 自动分割
- 分割后文件保持 `.log` 后缀
- 不压缩，保持原始格式
- 通过符号链接 `devices_op.log` 始终指向最新日志

**实现机制：**
1. **Fluentd 自动分割**：buffer 文件达到 100M 时自动 flush 为独立文件
2. **符号链接维护**：每分钟更新 `devices_op.log` 指向最新的 buffer 文件
3. **Logrotate 备用**：对已分割文件进行二次分割（如果单文件再次超过 100M）

**配置文件：**
- `tools/config/fluentd-docker.conf` - Fluentd 配置（100M 分割）
- `tools/config/device_op-logrotate.conf` - logrotate 配置（二次分割）
- `tools/crontab/update-device-op-symlink.sh` - 符号链接更新脚本（每分钟）
- `tools/crontab/logrotate-device-op.sh` - logrotate 检查脚本（每5分钟）

**目录结构：**
```
/home/smyze/logs/device_op/
├── buf/                                    # buffer 目录
│   └── buffer.b64df9110...log             # 当前正在写入的 buffer
├── devices_op.log -> buf/buffer.xxx.log   # 符号链接（始终指向最新）
├── devices_op_0.log                       # 已分割的日志文件
├── devices_op_1.log
└── devices_op_2.log
```

**文件命名规则：**
- 当前日志：`devices_op.log`（符号链接）
- 分割文件：`devices_op_{序号}.log`（如 `devices_op_0.log`）
- 二次分割：`devices_op_{序号}-{日期}-{时间戳}.log`（如需要）

**自动配置：**
启动脚本 `service-start-up.sh` 会自动配置 cron 任务和 sudo 权限，无需手动操作。

### 10.4 Fluentd 配置

**配置文件：** `tools/config/fluentd-docker.conf`

实际采用双路 copy 方案，保留原有日志的同时输出统一日志：

```ruby
<source>
  @type forward
</source>

# 提取 log 字段
<filter **>
  @type record_transformer
  renew_record true
  keep_keys log
</filter>

# 使用 copy + relabel 实现双路输出
<match **>
  @type copy

  # 输出 1: 原有日志文件（保留不变）
  <store>
    @type file
    path /fluentd/log/${tag}/docker
    append true
    <buffer tag, time>
      @type file
      path /fluentd/log/buf/docker
      flush_mode interval
      flush_interval 5s
    </buffer>
  </store>

  # 输出 2: 转发到 @device_op 标签做过滤
  <store>
    @type relabel
    @label @device_op
  </store>
</match>

# --- 设备操作日志处理 ---
<label @device_op>
  # 只保留包含 device_op 标识的日志
  <filter **>
    @type grep
    <regexp>
      key log
      pattern "log_type":"device_op"
    </regexp>
  </filter>

  # 写入统一文件
  <match **>
    @type file
    path /fluentd/log/device_op/devices_op.log
    append true
    add_path_suffix false
    <format>
      @type single_value
      message_key log
    </format>
    <buffer>
      @type file
      path /fluentd/log/buf/device_op
      flush_mode interval
      flush_interval 1s
    </buffer>
  </match>
</label>
```

**说明：**
- Fluentd 容器已挂载 `/home/smyze/logs:/fluentd/log`
- 统一日志输出到：`/home/smyze/logs/device_op/devices_op.log`（Fluentd 和 tools 宿主机脚本写入同一个文件）
- `add_path_suffix false` 确保文件名不带日期后缀，所有日志写入同一个 `devices_op.log`
- 1 秒刷新一次，准实时写入
- tools 宿主机脚本使用 `flock` 文件锁避免与 Fluentd 并发写入时行交错

### 10.5 总体技术架构

利用各语言生态的成熟框架能力，通过**分层组合**实现：

| 层 | 职责 | Java (bar-deploy-client) | Python (bar_middleware / orderStatusAgent) | C# (Quokka251) | Bash (tools) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 输出层 | JSON 输出到 stdout | Logback Console Appender + `LogstashEncoder` | loguru 输出到 `sys.stdout` (serialize=True) | Serilog Console Sink + `CompactJsonFormatter` | echo JSON 到 stdout |
| 上下文层 | trace_id / device_id 自动注入 | MDC + Filter + `MdcTaskDecorator` | `contextvars` + FastAPI 中间件 | Serilog `LogContext.PushProperty()` (AsyncLocal) | 环境变量 |
| 拦截层 | 关键路径自动记录 | AOP `@DeviceOpLog` 注解 | `@log_call` 装饰器 + requests `LoggingAdapter` | Task 入口 `using` scope | 手动调用 |
| 补充层 | 特定业务字段 | SLF4J fluent API `addKeyValue()` | `logger.bind()` | `LogContext.PushProperty()` | 函数参数 |

**核心原则：**
- 原有日志系统完全保留，统一日志是额外的一路 Sink/Appender 输出
- 上下文（trace_id、device_id、order_id）通过框架机制自动注入，不在业务代码中手动传递
- 关键路径通过 AOP/装饰器/中间件自动拦截，减少业务代码侵入
- 只在框架无法覆盖的地方手动补充

**B3. AOP 自动拦截 — `@DeviceOpLog` 注解**

新增自定义注解 + 切面，选择性拦截关键方法：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DeviceOpLog {
    String module() default "";
    String eventType() default "api";
}
```

```java
@Aspect
@Component
public class DeviceOpLogAspect {
    private static final Logger deviceOpLog = LoggerFactory.getLogger("device.op");

    @Around("@annotation(annotation)")
    public Object logDeviceOp(ProceedingJoinPoint joinPoint, DeviceOpLog annotation) throws Throwable {
        long start = System.currentTimeMillis();
        String method = joinPoint.getSignature().toShortString();

        if (!annotation.module().isEmpty()) {
            MDC.put("module", annotation.module());
        }
        MDC.put("event_type", annotation.eventType());

        try {
            Object result = joinPoint.proceed();
            long duration = System.currentTimeMillis() - start;
            deviceOpLog.atInfo()
                .addKeyValue("duration_ms", duration)
                .addKeyValue("status", "success")
                .log("完成: {}", method);
            return result;
        } catch (Exception e) {
            long duration = System.currentTimeMillis() - start;
            deviceOpLog.atError()
                .addKeyValue("duration_ms", duration)
                .addKeyValue("status", "error")
                .addKeyValue("exception", e.getClass().getSimpleName())
                .log("失败: {} - {}", method, e.getMessage());
            throw e;
        }
    }
}
```

**C3. 出站 HTTP 自动拦截 — requests LoggingAdapter**

替代在每个 `HttpCommand` 子类中手动埋点，通过 Transport Adapter 自动拦截所有出站 HTTP 错误：

```python
from requests.adapters import HTTPAdapter
import time

class DeviceOpLoggingAdapter(HTTPAdapter):
    """自动记录所有出站 HTTP 请求的错误到统一日志。"""
    def __init__(self, module="", module_id="", **kwargs):
        self.module = module
        self.module_id = module_id
        super().__init__(**kwargs)

    def send(self, request, **kwargs):
        start = time.perf_counter()
        try:
            response = super().send(request, **kwargs)
            duration = int((time.perf_counter() - start) * 1000)
            if response.status_code >= 400:
                device_op_logger(self.module, self.module_id).bind(
                    duration_ms=duration,
                    details={"action": f"{request.method} {request.url}",
                             "status": "fail", "duration_ms": duration}
                ).error(f"HTTP错误: {request.method} {request.url} status={response.status_code}")
            return response
        except Exception as e:
            duration = int((time.perf_counter() - start) * 1000)
            device_op_logger(self.module, self.module_id).bind(
                duration_ms=duration,
                details={"action": f"{request.method} {request.url}",
                         "status": "fail", "duration_ms": duration}
            ).error(f"请求异常: {request.method} {request.url} - {e}")
            raise
```

各硬件模块的 `HttpCommand` 使用时挂载对应 Adapter：
```python
# 例如 CupDispenser
session = requests.Session()
session.mount("http://", DeviceOpLoggingAdapter(module="CupDispenser", module_id="CD_01"))
```

这样所有通过该 session 发出的 HTTP 请求，错误会自动写入统一日志，无需修改 `handle_error()` 内部逻辑。

**C4. @log_call 装饰器 — 关键函数自动记录**

```python
import functools, time

def log_call(module: str, module_id: str = "", event_type: str = "operation"):
    """装饰器：自动记录函数的执行结果和异常到统一日志。"""
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            start = time.perf_counter()
            try:
                result = func(*args, **kwargs)
                duration = int((time.perf_counter() - start) * 1000)
                device_op_logger(module, module_id, event_type).bind(
                    duration_ms=duration
                ).info(f"{func.__name__} 完成")
                return result
            except Exception as e:
                duration = int((time.perf_counter() - start) * 1000)
                device_op_logger(module, module_id, event_type).bind(
                    duration_ms=duration
                ).error(f"{func.__name__} 失败: {e}")
                raise
        return wrapper
    return decorator
```
